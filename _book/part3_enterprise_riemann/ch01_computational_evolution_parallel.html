第III-1章 金融工学における計算技術の発展と並列コンピューティング

金融工学は、数学理論だけで発展してきたのではない。1960年代以降、金融理論の発展とコンピュータの発展は互いに影響しながら進んできた。理論上は表現できても計算できなかった問題が、計算機能力の向上によって実務へ取り込まれ、逆に金融商品の複雑化が新しい計算技術を必要としてきた。

本章では、まずこの約60年の流れを大きく振り返る。次に、2020年代にCloud、HPC、GPU、Open Source Software、Tensor計算Libraryがそろったことで、金融計算がどこまで変わったのかを整理する。そのうえで、第III部前半の出発点として、一台のPCの複数Coreを利用する並列計算をRのfuture / furrrで実装する。

第III部全体の中心にあるのは、金融計算を高速化する二つの方向である。一つは、CPU、GPU、Grid、Cloudなどの計算資源を拡張するHardware / Infrastructure Accelerationであり、もう一つは、Automatic Differentiationによって計算方法そのものを変えるAlgorithmic Accelerationである。

III-1.1 金融工学とコンピュータの60年

1960年代から1970年代にかけて、Portfolio Theory、CAPM、Black-Scholes / Mertonモデルなど、現代金融工学の基礎となる理論が整備された。当時の計算資源は現在と比べて極めて限られており、実務へ取り込みやすいモデルは解析解を持つものが中心であった。

1973年のBlack-Scholes / Mertonモデルは、その象徴的な例である。European Optionの価格を

\[ C=C(S,K,r,\sigma,T) \]

とすると、Delta、Gamma、VegaなどのGreeksも解析的に表すことができる。

しかし1980年代以降、早期行使、経路依存性、複雑なPayoff、複数のリスクファクターを持つ商品が増えるにつれて、閉形式の解析解だけでは十分でなくなった。PDE、Finite Difference、Binomial / Trinomial Treeなどの数値計算が実務へ広がった。

1990年代にはMonte Carlo Simulationが、複雑なデリバティブ評価やVaRをはじめとするリスク管理の重要な計算基盤となった。価格は多数のPathまたはScenarioの平均として、概念的に

\[ \hat V = \frac{1}{M} \sum_{m=1}^{M}V^{(m)} \]

と評価される。Path数を増やせば統計的精度を高められる一方、計算量も増加する。さらにPortfolio、Scenario、Risk Factorが増えると、必要となるPricing回数は急速に膨らむ。

2000年代には、大規模Portfolioや複雑なExotic / Hybrid商品の評価を支えるため、金融機関でOn-premise Grid Computingが広く利用されるようになった。PortfolioやScenarioを多数のJobへ分割し、Schedulerが複数のServerへ配布するという構造である。

同じ時期、CPUは単純なClock Speedの向上からMulti-core化へ進んだ。一台のServer内部でも複数のTaskを同時に実行できるようになり、金融計算は「一つずつ順番に計算する」構造から「独立した計算を分割して同時に処理する」構造へ移っていった。

2010年代にはGPUによるMassive Parallel ComputingとCloud Computingが急速に普及した。Monte Carloのように、同種の計算を多数のPathへ適用する処理はGPUと相性がよく、Tensor演算によって大規模な計算をまとめて処理できるようになった。

この流れを大きく整理すると、次のようになる。

III-1.2 2020年代に変わった金融計算の前提

2020年代の変化は、単にコンピュータが高速になったことではない。大きいのは、計算資源を「所有する」ことから、必要なときに必要な規模だけ「利用する」方向へ移ったことである。

従来のOn-premise環境では、大規模な計算を行うにはServer、Storage、Network、Schedulerなどを自ら用意し、最大負荷を想定した設備投資を行う必要があった。現在はCloudやHPC Serviceを利用することで、計算負荷に応じてCPUやGPUを柔軟に追加できる。SaaS型・Managed Service型の計算基盤も増え、インフラの構築と保守に必要な負担は大きく低下した。

同時に、RやPythonを中心とするOpen Source Softwareが成熟した。数値計算、統計、最適化、Machine Learning、Distributed Computing、GPU Tensor計算を、商用の専用計算環境だけに依存せず組み合わせることができる。

この二つが重なることで、以前は大規模金融機関の専用Gridでなければ現実的でなかった計算を、より安価かつ柔軟な環境で実行できるようになった。問題設定と計算環境によって必要時間は大きく異なるものの、数百万から数千万、さらに十分なGPU / HPC資源を用いる場合には数億Path規模を視野に入れたMonte Carlo Simulationも現実的な設計対象となっている。

On-premise Hardware
        |
        v
Elastic Cloud / HPC
        +
Open Source Software
        +
CPU / GPU Tensor Computing
        |
        v
Massive Monte Carlo

III-1.3 ハードウェア高速化だけでは残る問題

計算資源を増やすことで、一回のPricingは速くできる。しかしRisk SensitivityをBump & Revalueで求める場合、Risk FactorごとにPricingを繰り返す構造は残る。

例えば中心差分では、

\[ \frac{\partial V}{\partial x} \approx \frac{V(x+h)-V(x-h)}{2h} \]

となる。Risk Factorが100個あれば、多数のBumpを作り、そのたびに大規模Monte Carloを再実行する必要がある。

したがって、

\[ \boxed{ \text{More Cores / More GPUs} \neq \text{Fewer Revaluations} } \]

である。Hardwareを増やすだけでは、Bump & RevalueというAlgorithmそのものが要求する再計算回数は減らない。

III-1.4 自動微分が実用技術になった理由

Automatic Differentiation自体は新しい数学ではない。しかし近年、TensorFlow、Keras、PyTorch、Rのtorchなど、Deep Learningの発展によって成熟したTensor計算Libraryが、安価で安定したAutomatic Differentiation環境を提供するようになった。

これらのLibraryでは、PricingをTensor演算として記述すると、その計算過程がComputational Graphとして保持される。最終的な価格からReverse ModeでGraphを逆向きにたどることで、多数の入力Risk Factorに対するGradientを効率的に取得できる。

\[ (x_1,x_2,\ldots,x_n) \longrightarrow \text{Monte Carlo Pricing} \longrightarrow V \]

に対して、

\[ \nabla V = \left( \frac{\partial V}{\partial x_1}, \ldots, \frac{\partial V}{\partial x_n} \right) \]

を求める。厳密にはForward Pricingに続いてBackward Passを行うが、Risk Factorごとに独立したMonte Carlo Pricingを何度もやり直す必要はない。

ここで金融計算は、

\[ \boxed{ \text{Hardware Acceleration} \longrightarrow \text{Hardware + Algorithmic Acceleration} } \]

へ進む。

III-1.5 第III部で扱う二つの計算技術

第III部では、この二つの方向をRで実装する。

前半の第III-2章から第III-4章では、future / furrrを出発点として、PC内の並列処理、非同期実行、Job / Task Control、分散計算、そしてエンタープライズ金融計算システムの構造を扱う。計算をどのように分割し、どこで実行するかが中心となる。

後半の第III-5章から第III-7章では、Rのtorchを用いてAutomatic DifferentiationによるRisk Sensitivityを実装する。対象はOptionからYield Curve、さらにPRDCの多因子Riskへ段階的に拡張する。

\[ \text{Option Greeks} \longrightarrow \text{Interest Rate Curve Risk} \longrightarrow \text{PRDC Multi-factor Risk} \]

本部全体の到達点は、次の形で表すことができる。

\[ \boxed{ \text{Scale Up / Scale Out} + \text{Automatic Differentiation} = \text{Enterprise Differentiable Risk Engine} } \]

まず本章では、その第一歩として一台のPCの中で計算を分割し、複数Workerへ配布する並列計算を実装する。

III-1.6 Rによる並列コンピューティング

Rではpurrrによる逐次処理と、future / furrrによる並列処理をよく似た形で記述できる。 金融計算では、入力データをtibbleとして保持し、Pricing Functionを各行へ適用する構造にすると、 逐次計算から並列計算へ移行しやすい。

              v
        Pricing Function
              |
        +-----+-----+
        |           |

        |           |

              |

III-1.6.1 現在価値計算のタスク化

まず、単純な現在価値計算をTaskとして定義する。

calculate_present_value_LFL <- function(cashflow, discount_rate, maturity) {
  tibble(
    cashflow = cashflow,
    discount_rate = discount_rate,
    maturity = maturity,
    present_value = cashflow / (1 + discount_rate)^maturity
  )
}

計算対象をtibbleとして用意する。

tbl_calculation <- tribble(
  ~scenario_ID, ~cashflow, ~discount_rate, ~maturity,
  1L, 100, 0.010, 1,
  2L, 100, 0.015, 2,
  3L, 100, 0.020, 3,
  4L, 100, 0.025, 4,
  5L, 100, 0.030, 5,
  6L, 100, 0.035, 6
)

III-1.6.3 マルチコアによる並列計算

次にfuture::multisessionを利用してWorkerを起動する。 利用可能なCoreをすべて占有せず、この例では最大2 Workerに制限する。

available_cores <- future::availableCores()
workers <- max(1L, min(2L, available_cores - 1L))

future::plan(
  future::multisession,
  workers = workers

tbl_future_setting <- tibble(

III-1.7 並列化による処理時間の短縮

小さすぎるTaskではWorker生成やデータ転送のOverheadが支配的になり、 並列化が必ずしも高速になるとは限らない。 そこで、一定時間を要する独立Taskを使って逐次処理と並列処理を比較する。

calculate_task_LFL <- function(task_ID) {
  Sys.sleep(0.10)

  tibble(
    task_ID = task_ID,
    result = sqrt(task_ID)
  )
}

vec_task_ID <- seq_len(12L)
sequential_time <- system.time(
  tbl_sequential_benchmark <- purrr::map(
    vec_task_ID,
    calculate_task_LFL
  )
)[["elapsed"]]
future::plan(
  future::multisession,
  workers = workers
)

parallel_time <- system.time(
  tbl_parallel_benchmark <- furrr::future_map(
    vec_task_ID,
    calculate_task_LFL,
    .options = furrr::furrr_options(seed = TRUE)
  )
)[["elapsed"]]

future::plan(future::sequential)
tbl_benchmark <- tribble(
  ~method, ~elapsed_seconds,
  "purrr::map", sequential_time,
  "furrr::future_map", parallel_time
) |>
  mutate(
    relative_to_sequential = elapsed_seconds / sequential_time
  )

show_table_LFL(tbl_benchmark)
#> # A tibble: 2 × 3
#>   method            ela_secon rel_seque
#>   <chr>                 <dbl>     <dbl>
#> 1 purrr::map           1.3300    1     
#> 2 furrr::future_map    1.45      1.0902

この例の目的は特定の高速化率を保証することではない。 重要なのは、同じPricing Functionを多数の独立Taskへ適用する場合、 Taskを複数Workerへ配分することで実行時間を短縮できるという構造である。

III-1.8 一台のPCにおける並列化の限界

Multi-coreによる並列化には明確な限界がある。 一台のコンピュータで利用できるCPU Core、Memory、GPUなどの計算資源には上限があるためである。

さらに実務のRisk Calculationでは、数件のTaskではなく、

  • 数十万件のTrade
  • 多数のMarket Scenario
  • Monte Carlo Path
  • Stress Scenario
  • Sensitivity Calculation

を同時に処理することがある。

この規模になると、一台のPCのCoreを増やすだけでは対応できない。 必要になるのは、Taskを複数のコンピュータへ配布する仕組みである。

\[ \boxed{ \text{Single Machine Parallelism} \longrightarrow \text{Distributed Computing} } \]

また、計算資源を増やしてPricingを高速化しても、SensitivityをBump & Revalueで求める場合には、 リスクファクターごとにPricingを繰り返す構造そのものは残る。 この問題は、本部後半の自動微分で改めて扱う。

III-1.9 まとめ

本章では、金融工学の計算が解析解から数値計算、Monte Carloへ発展するにつれて計算量が増大し、 その対応としてMulti-core CPUや並列処理が重要になったことを確認した。

Rではfuture / furrrを利用することで、逐次計算の構造を大きく変えずに 一台のPC上で複数WorkerへTaskを配分できる。

しかし、エンタープライズ金融計算では一台のPCだけでは計算資源が不足する。 次章では、Taskを複数の計算機へ配布する分散コンピューティングとJob / Task Controlへ進む。
